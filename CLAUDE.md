# CLAUDE.md — Amethyste-Idle

MMORPG navigateur web retro (Zelda + FF7/8/9 + stein.world). Vue 2D top-down, tiles 32x32, sprites RPG Maker VX.

## Regles absolues

1. **Docker obligatoire** : TOUTES les commandes PHP/Symfony/Composer s'executent dans le conteneur Docker :
   ```bash
   docker compose exec php php bin/console <commande>
   docker compose exec php composer <commande>
   ```
   Ne JAMAIS executer `php`, `composer`, `symfony` directement sur la machine hote.

2. **Pas de Node.js** : le projet utilise Symfony AssetMapper (importmap). Pour ajouter un package JS :
   ```bash
   docker compose exec php php bin/console importmap:require <package>
   ```
   Ne JAMAIS utiliser npm, yarn, webpack, vite.

3. **Commits atomiques** : un seul commit par changement fonctionnel testable.

4. **Tester avant de continuer** : verifier chaque modification avant de passer a la suivante.

5. **Langue** : communiquer en francais avec l'utilisateur.

6. **Pas de niveau global** : la progression est par arbres de talent/domaine uniquement. Ne jamais introduire un systeme de "level up" global.

7. **Position = zone (pivot PBBG)** : la reference de position d'un joueur est `Player::currentZone` (FK vers `Zone`, maintenue par `ZoneTravelService`). Toute logique de position s'appuie sur la zone, JAMAIS sur les coordonnees. Le code carte navigable (rendu PixiJS, pathfinding, mouvement, editeur admin, terrain) a ete **supprime avec ZON-21** ; les coordonnees `"x.y"` (`getX()`/`getY()`) subsistent comme champ herite sur `Player` sans logique de deplacement.

8. **Taille des phases** : si une phase ou feature semble trop volumineuse (taille L ou XL, ex: 400+ lignes de fixtures, 10+ fichiers a modifier), la decouper en sous-phases realisables en une seule session. Chaque sous-phase doit etre commitable et testable independamment. Ne jamais tenter d'ecrire plus de ~200 lignes de donnees/fixtures en une seule passe.

9. **Competences = PASSIVES UNIQUEMENT** : les skills des arbres de talent ne donnent JAMAIS de sort actif directement. Les skills servent a :
   - **Debloquer l'utilisation d'une materia** (`actions.materia.unlock`) — prerequis pour equiper/utiliser une materia specifique
   - **Accorder des bonus passifs** — stats (damage, heal, hit, critical, life)
   - **Permettre d'equiper certains objets** — prerequis d'equipement
   Ne JAMAIS utiliser `actions.combat.spell_slug` dans un skill. Utiliser `actions.materia.unlock` a la place.

10. **Sorts actifs = UNIQUEMENT via materia** : pour lancer un sort en combat, le joueur doit (1) posseder la materia, (2) avoir appris la competence materia correspondante dans un arbre, (3) avoir sockette la materia dans un slot d'equipement. L'attaque de base de l'arme est toujours disponible gratuitement.

11. **Pas de PvP** : le jeu est exclusivement PvE cooperatif. Ne jamais introduire de combat joueur contre joueur (arenes, duels, zones PvP, RvR). Les interactions entre joueurs sont limitees a la cooperation (guildes, groupes, commerce, chat).

12. **Multi-personnages** : un compte utilisateur (User) peut posseder plusieurs personnages (Player). La limite par defaut est de **1 personnage par compte** (configurable, cas particuliers possibles). Le systeme de creation de personnage (choix du nom, de la race, de l'apparence) est distinct de l'inscription du compte.

## Conventions de code

- **PHP** : PSR-12, attributs PHP 8 (`#[Route(...)]`), readonly constructor promotion
- **JS** : ESM (import/export), Stimulus controllers avec `static values`/`static targets`
- **Entites** : traits partages (`CharacterStatsTrait`, `CoordinatesTrait`, `TimestampableEntity`)
- **Evenements** : architecture Event-Driven (actions -> Events -> EventSubscribers)
- **Collisions** : bitmask directionnel N/S/E/W, -1 = mur impassable
- **Nommage** : PascalCase entites, camelCase methodes, snake_case routes
- **Systeme de design** : `assets/styles/design-system.css` porte les tokens (`@theme`) et les
  composants `.ds-*` (boutons, cartes, sceaux de rarete, jauges, lignes d'objet, etats vides).
  Un ecran repris utilise ces composants ; il ne redeclare pas de couleur. Les rampes Tailwind
  heritees (`gray-*`, `purple-*`, `text-white`…) sont **reindexees** vers le parchemin pour que
  les ecrans pas encore repris restent coherents : c'est un pont, pas une API. Trois regles
  tenues par les composants : une seule action primaire par ecran, tout chiffre en monospace,
  un etat vide qui dit quoi faire. Reference visuelle : `design/Amethyste - Design System.dc.html`.
- **Tailwind 4 uniquement** : plus aucun CDN Tailwind 2 n'est charge (il gagnait sur la feuille
  compilee, les regles hors calque l'emportant sur celles d'un `@layer`). Les noms d'avant la v4
  sont refuses par `LegacyTailwindScanner` : utilitaires d'opacite (`bg-opacity-50` ->
  `bg-noir/50`), renommages v3 (`flex-shrink-0` -> `shrink-0`), `bg-gradient-to-*` ->
  `bg-linear-to-*`, et `outline-none` -> `outline-hidden` (en v4, `outline-none` supprime le
  contour au lieu de le rendre transparent, et le repere de focus disparait en contraste force).
  Attention aux echelles decalees d'un cran : le `shadow-sm` de la v4 vaut l'ancien `shadow`,
  son `blur-sm` vaut l'ancien `blur`. Les anciennes valeurs s'ecrivent `shadow-xs` et `blur-xs`.

## Pieges courants

- `public/assets/` compile ecrase l'AssetMapper dev -> `rm -rf public/assets/` si comportement JS inattendu
- Mercure integre dans Caddy, pas de serveur separe a demarrer
- En dev, le volume Docker monte `.:/app` -> les fichiers sont partages entre hote et conteneur
- `tailwind:build` doit tourner avant `asset-map:compile` ou `debug:asset`
- **Migrations PostgreSQL** : `ADD CONSTRAINT IF NOT EXISTS` n'existe PAS en PostgreSQL. Pour une contrainte idempotente, utiliser un bloc `DO $$ BEGIN IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname = 'nom') THEN ALTER TABLE ... ADD CONSTRAINT ...; END IF; END $$`. En revanche, `ADD COLUMN IF NOT EXISTS`, `CREATE TABLE IF NOT EXISTS` et `CREATE INDEX IF NOT EXISTS` sont valides.
- **Ordre des migrations le meme jour** : Doctrine trie les migrations par ordre alphabetique du nom de version (`VersionYYYYMMDD<Suffixe>`), PAS par heure de creation. Deux migrations du meme jour sont donc executees dans l'ordre alphabetique de leur suffixe, pas dans l'ordre logique/chronologique voulu. Si une migration `B` (ex: `Version20260726GardenPlot`) reference une table creee par une migration `C` du meme jour (ex: `Version20260726PlayerHouse`), et que `B` < `C` alphabetiquement, le deploiement casse (`relation "x" does not exist`) — vu en prod le 2026-07-27 (`ZoneGraph` vs `PlayerCurrentZone`/`WorldEntitiesZone`/`ZoneGatherVeins`, puis `PlayerHouse` vs `GardenPlot`/`HouseFurnishing`/`HouseRent`). Fix : renommer (fichier + classe) la migration qui cree la table en prefixant son suffixe par une lettre qui la trie avant ses dependantes (convention deja utilisee pour `Version20260326ZGuildInfluence`). Avant d'ajouter plusieurs migrations le meme jour, verifier que celle qui cree une table/colonne est bien triee alphabetiquement avant celles qui la referencent.

- [docs/GAME_ARCHETYPES.md](docs/GAME_ARCHETYPES.md) — **Archetypes de combat et equilibrage des arbres** (proposition instruite, 2026-07-31) : ce qui manque a GAME_DOMAINS pour que deux arbres ne se ressemblent pas. Un arbre ne contient que des **acces, des passifs et des accords** — les actions sont dans la materia (regles 9 et 10) : *l'archetype n'est donc pas dans l'arbre, il est dans le couple (arbre, materia qu'il ouvre)*. Sept decisions : la **fonction** comme 3e axe du domaine (assaut / controle / entretien / encaisse, qui distingue enfin les trois arbres d'eau × sorts) ; **une ressource par registre** (sorts → PM, melee → temps de reprise, distance → **munitions**, seul cout economique du jeu) ; **le geste d'arme est une materia** (`Spell::register` — sans quoi un arbre de melee ne qualifie **aucune action**, l'attaque de base ne lisant pas les passifs) ; un **vocabulaire ferme de 15 leviers en pourcentage** avec taux de change (les 5 stats plates sont ineequilibrables : `damage: +1` vaut +50 % sur un geste a 2 degats et +8 % sur un geste a 12) ; le geste porte **deux etiquettes de plus** — `intent` (degat/soin/protection/amelioration/entrave) et `scope` (soi/allie/groupe/cible) —, ce qui ferme la boucle « arbre x materia » : la **palette d'intentions** dit quelles materia un arbre a le droit d'ouvrir ; les **passifs conditionnels d'equipement** (« +10 % a la dague », « −8 % de degats subis avec un bouclier », « +4 % de vitesse en cuir ») avec multiplicateurs ×1,4 (build) et ×2,0 (combat) — le budget compte l'effet **moyen**, pas l'effet affiche —, ce qui fait enfin de l'equipement un build et donne envie de panacher ; un **budget de puissance** (50 points de budget par arbre, grille 3/6/9/14, plafond par levier, regle des 80/20 par palette) ; l'**echelle de cout** 0/10/25/50/100 derivee d'un calendrier, et le gain de points **indexe sur le palier de l'adversaire** (on ne monte pas un arbre en tapant des rats) ; le **capstone conditionnel**. Plus la **loi du depot** (§7 bis) : le donjon de groupe etant semi-synchrone (un joueur actif a la fois, tour d'un absent resolu tout seul), **un geste qui touche le groupe ne reagit pas, il depose une duree** — regeneration, absorption, amelioration posees a son tour et qui courent sur les tours des autres, connecte ou non, la duree comptee **en tours de la rencontre**. Le soigneur ne soigne pas : il provisionne. Plus cinq nuances : **une marque par element** (Brulure, Trempe, Desequilibre, Alourdi, Entaille, Traque, Revele, Aveugle — sans elles le capstone d'assaut, le levier `grip` et la palette de controle n'ont aucun objet) ; **la munition porte l'element** — l'archer est le seul qui *achete* son element, donc le registre le plus souple et le plus cher ; **un trait par famille d'arme et trois profils d'armure** (le cuir evite, la plaque absorbe : meme total, deux jeux) ; **la fourche** — au palier 3 l'arbre ecrit 60 points de budget et le personnage en porte 50, ce qui fait que **deux pyromanciens finis cessent d'etre identiques** (reutilise `other_branch`, livre par DOM-06) ; et **le pacte** — un malus rend du budget (« +19 % de degats, −15 % de PV »), la seule mecanique qui rende un personnage mesurablement plus faible quelque part. Plus les **six tests** d'un arbre (dont *le test de l'arbre nu* : retirez les accords, l'archetype doit rester lisible), **quatre arbres ecrits en entier avec leurs deux branches** (Pyromancien, Guerisseur, Soldat, Archer — un par fonction) et **un exemple deroule du jour 3 au mois 3** (§9 bis, le soldat Roshen : son premier combat, la condition du bouclier qui s'allume, le choix de fourche tel qu'il le voit, l'elite affrontee par les deux branches tour par tour, et le donjon ou le depot d'un allie survit a sa deconnexion). **L'exemple a produit trois corrections** : la fourche porte aussi un **accord** — sans quoi deux branches donnent le meme combat au tour pres (11 contre 11) —, **toute protection se depose** (une garde qui ne couvre que son propre tour punit l'encaisse de se defendre), et **le multiplicateur de condition suit la frequence mesuree** (« vous avez encaisse au tour precedent » est vraie des le tour 2 : ×1,4, pas ×2,0). Constat qui confirme la these du document en la chiffrant : **+9 % sur un levier ne retire pas un seul tour de combat** — l'identite est dans les gestes, pas dans les pourcentages. **Un second exemple** (§9 ter, le guerisseur seul puis en donjon) a produit trois corrections de plus : l'ancre d'echelle a besoin d'une **seconde moitie** — le cout d'une rencontre **en ressource, rapporte au budget du jour** (un soldat et un guerisseur tiennent onze tours tous les deux, mais l'un n'a rien depense et l'autre a vide 108 PM sur 120 ; sur les ~16 combats d'une journee ils n'ont rien a voir) ; **la duree d'un depot etale sa valeur, elle ne l'augmente pas** (sinon un depot de 10 tours a quatre vaut 14,7 tours d'attaque et un groupe sans guerisseur devient non viable) ; et **les marques se portent des deux cotes** (21 monstres sur 65 ont un sort, 9 appliquent un statut — `ward` est dans deux palettes sur quatre et n'aurait rien a resister). **Un troisieme exemple** (§9 quater, l'archer sur une journee) a trouve le defaut que les deux autres ne pouvaient pas voir : la munition portant l'element, une **fleche ordinaire** produisait une action **sans element**, donc hors de la case du domaine, donc **sans aucun passif d'arbre** — le filet de securite eteignait l'archetype. L'element vient donc de la materia, la munition le **remplace** ; l'archer n'achete pas sa puissance, il achete sa souplesse. Plus trois corrections chiffrees : sans **prime de munition**, l'archer paie **90 a 230 gils par jour pour +1,8 % de degats** face a un pyromancien qui ne paie rien ; sans **capacite de carquois**, `wind` — 18 % du budget d'un arbre — rend **12 gils par jour** ; et le prix d'une munition se calibre **contre le revenu du jour**, jamais contre la valeur du geste. **Un quatrieme exemple** (§9 quinquies, l'hydromancien, le seul qui ait **infirme** une affirmation du document) : le §5 disait qu'un tour vole a l'adversaire est un tour de degats evite, donc que le controle est offensif. **En duel c'est arithmetiquement nul** — les degats subis sont identiques (101) qu'on pose zero ou trois entraves, le combat s'allongeant exactement de ce qu'on a vole. D'ou : **une entrave n'est jamais un tour perdu** (duree >= 2, ou marque portee par un geste de degat — ce qui fait de `grip` la condition d'existence de la fonction), et **l'asymetrie du donjon semi-synchrone** : un effet pose sur les **allies** se multiplie par leur nombre (x8,8 a quatre), un effet pose sur l'**ennemi** ne se multiplie pas (x0,9), puisqu'un seul joueur agit par tour — entretien et encaisse gagnent au groupe, assaut et controle non. Sa compensation : le controle est **la seule fonction dont la valeur ne change pas** entre le solo et le groupe. **La comparaison croisee** (§9 sexies, les six builds sur la meme ligne — ce qu'aucun exercice isole ne pouvait voir) conclut que **les arbres ne sont PAS equilibres** : le guerrier tue aussi vite que l'hydromancien, survit mieux que tout le monde et ne paie rien, quand l'archer gagne deux tours pour 230 gils/jour et le pyromancien finit a 11 PV en panne de PM. Trois causes mesurees : les leviers de survie rendent **2,5x** les leviers de degats a budget egal ; une ressource payee n'est jamais compensee ; et surtout **la vitesse n'a aucune valeur dans ce jeu** — une chasse coute 5 points d'energie quel que soit le nombre de tours, donc tuer en 7 tours au lieu de 14 ne permet pas un combat de plus. D'ou trois corrections (le **palier des accords suit la fonction** : assaut au palier plein, les autres a −25 %, ce qui creuse l'ecart a 7 tours contre 11-14 sans toucher un levier ; la prime de munition **chiffree** ou supprimee ; l'**ancre de fonction** — meme nombre de rencontres par jour, seule la facon de payer differe) et **un arbitrage a rendre** : donner une valeur a la vitesse, par des **rencontres a fenetre** (mesure : contre un boss de 400 PV, l'archer et le pyromancien tiennent la fenetre 12-20 tours, le soldat et le guerisseur non). Sans ce contenu, l'assaut n'a pas de raison d'exister. **La simulation d'une journee** (§9 septies, 14 communs + 2 elites) **renverse le classement** : sur un combat le guerrier domine, sur une journee c'est le **guerisseur** (70 PV perdus contre 494 a 710) et le tank pur devient le **pire des six** — la lenteur se paie en coups recus, et la vitesse EST de la survie. Deux corrections en sortent : **les munitions cessent d'etre un consommable payant** (aucun archetype ne porte un cout recurrent en gils que les autres n'ont pas — le carquois devient une piece d'equipement durable qui se vide dans la rencontre et se ramasse apres, et la ressource du registre distance devient intra-rencontre comme les PM) ; et **les PM regenerent hors combat comme les PV** (12 s/PV livre, ~6 s/PM a calibrer — BALANCE §24.2), sans quoi l'entretien joue trois fois plus de contenu que les autres. Converti dans la seule monnaie commune — du temps —, les six builds tiennent alors entre **99 et 179 minutes** d'attente quotidienne. Plus la **matrice contexte x fonction** et la regle qui la tient : **toute fourche oppose deux contextes**, une branche jouable seul et une branche qui sert le groupe (la Ligne mobile / le Mur). Enfin (§9 octies) **les degats subis, et ce qu'une elite doit etre** : sur le tout-venant l'ecart est faible (16 a 26 % de sa barre — la mitigation du tank compense sa lenteur, la vitesse de l'assaut compense sa fragilite), mais sur l'elite **tout le monde survivait**. Decision : **une elite n'est pas un palier solo** — a frappe ~2,9x celle d'un commun du meme palier (26 contre 9) pour ~1,8x ses PV, les six builds y laissent **102 a 129 % de leur barre**, uniformement, sans qu'aucun ne s'en sorte par une astuce. Et elle devient normale a quatre **sans regle speciale** : les degats ne se divisent pas par la taille du groupe, mais les depots, si. Conséquences a porter dans **GAME_BESTIARY** (le rang Elite tue un solo, ce n'est pas un commun gonfle) et **GAME_DUNGEONS** (l'elite est l'etape normale d'un donjon ; en zone on doit pouvoir la fuir). **Statut des chiffres (§0.2)** : **aucun nombre du document n'est une valeur de jeu** — tous sont des reperes calcules a la main sur une echelle illustrative. Le document dit lesquels **survivront** a la recalibration (les regles et les rapports : une entrave d'un tour est nulle, etat x N contre action x 1, N x X <= 100, la duree etale sans augmenter, une elite tue un solo, l'identite est dans les gestes) et lesquels **seront recalcules** (tous les PV et degats, la mitigation des armures, la borne d'aggro, `encounter_hp_per_member`, les taux de change des leviers, les minutes d'attente). Consequence de methode : **on ne recalibrera pas a la main** — la suite passe par **`app:balance:simulate`** (ARC-17), soeur dynamique de `app:balance:report`, qui lit les vraies donnees, genere les builds de reference, rejoue les cinq scenarios et tient les seuils en CI. Les tableaux du document sont sa **specification**. **Armures actees le 2026-08-01 : plaque 40 %, cuir 20 %, tissu 0 %** (ecart de PV effectifs x2,3 / x1,6 / x1) — la borne haute etant 50 %, point ou la mitigation annule exactement la lenteur du tank. Enfin (§13) **les formes de geste** : le vocabulaire d'intentions dit ce qu'un geste **fait**, jamais sa **forme** — et c'est la que vivent les archetypes des autres MMO. Huit formes empruntees, **chacune reparant un defaut mesure** : le **familier** (le tour d'un absent ne produit qu'une attaque de base — c'est le depot qui *agit*), la **charge** (la melee n'a aucune raison d'aimer les longs combats), le **transfert** (l'aggro est impossible sur une rencontre a PV partages), la **riposte** (le tank ne tue pas), l'**ouverture** (`tempo` n'a aucun effet modelise), la **conversion** (le pyromancien paie deux fois), la **posture** (aucun choix a l'echelle d'une rencontre) et le **differe** (la seule forme qui *exploite* l'asynchronie au lieu de la subir). **Aucune ne demande une cinquieme fonction** — ce qui manquait n'etait pas un role, c'etait un vocabulaire du cote de la materia. Plus **sept refus**. **Deux arbitrages rendus le 2026-08-01** : (1) le **familier est un depot offensif, pas un acteur** — retirez le ciblage et il ne reste qu'une chose qui frappe chaque tour pendant une duree, donc le critere d'admission impose de le traiter comme tel ; on garde ce qui comptait (il agit sur les tours ou son invocateur est absent) et la fiction entiere, on economise un acteur, une IA et une cible (cout L → M). **Correction 21, trouvee le 2026-08-01** en cherchant si un invocateur en tissu devenait trop puissant : le danger n'etait pas la fragilite du tissu — le familier ne mitige rien, un invocateur en tissu reste aussi fragile qu'un mage — mais le fait que **le familier agit sur les tours de la RENCONTRE quand son invocateur n'a que les SIENS**, soit un taux de change de 4 pour 1 en groupe. Mesure avec la calibration initiale (x2,4 le tour investi) : l'invocateur contribuait **+87 %** avec quatre invocations, et plus il invoquait plus il gagnait. La correction 5 (*la duree etale, elle n'augmente pas*) etait deja ecrite mais pas appliquee : **la valeur totale d'un familier vaut ~1 tour d'attaque**, ce qui le met **a l'equilibre quand le joueur est present** et **+56 % sur six tours d'absence**. D'ou une regle generale : *un depot **offensif** ne depasse jamais un tour d'attaque par tour investi ; un depot **defensif** peut valoir davantage, parce que la barre de vie de sa cible l'ecrete toute seule* — c'est ce qui autorise x8,8 pour un soin de groupe et interdit x2,4 pour des degats ; (2) **l'aggro entre, bornee** — le refus reposait sur le modele actuel du donjon, que **DON-02/03 change** (vrais monstres, vraie riposte). Par defaut chacun encaisse la riposte de ses propres actions ; un geste de menace en deplace **au plus la moitie** ; **la table de menace reste refusee** (aucun score cumule). Prerequis chiffre : **la plaque doit porter ~−30 %** — l'ecart tank/tissu par l'arbre seul est de x1,39, encaisser la part de quatre en demanderait x4, soit 47 des 50 points de budget rien qu'en `guard` : **la mitigation d'un tank vient de son armure, pas de son arbre** (GAME_ITEMS). Defaut trouve au passage : `zone.dungeon.encounter_hp_per_member` (200) est calibre pour une rencontre **sans riposte** — le jour ou DON-03 la branche, 800 PV pour quatre rendent le soigneur **obligatoire** ; a ~120. Regle qui le remplace : *une rencontre de groupe se calibre sur le **pool de PV du groupe**, jamais sur un multiple du nombre de joueurs*. Plus la mesure qui separe enfin deux arbres de sorts : le pyromancien qui enchaine ses Nova **tombe en panne au tour 8**, le guerisseur tient au-dela de 40, la grille des 24 domaines, trois melanges (le tank en cuir a bouclier, le duelliste a deux dagues, le soutien de donjon), les **accointances** (une synergie ne donne jamais de puissance, seulement de la souplesse — les `DomainSynergy` livrees sont une fuite de budget : `damage +10` hors de tout arbre) et **le plafond global de 500 points supprime** — il contredisait « le savoir n'est jamais borne », et un seul arbre en consommait 465 (amendement porte dans GAME_DOMAINS §1). **Six decisions ajoutees le 2026-08-01**, tirees de l'exercice de GAME_TREE_ANATOMY : le **placement du pacte** (§6.5 — il remplace un passif de fourche, jamais un 19e nœud ; grille a deux crans 5/10 pb ; regle 7 : *un arbre a pacte est un autre arbre*), la **loi des prerequis internes** (§6.6, decision 21 — le capstone exige l'accord de branche, jamais ses passifs), et le **plafond du capstone** (§7.1, decision 22 — un levier de plafond ≥ 14 pb, 7 leviers exclus d'office, **et son levier jamais au palier 3** : 14 + 9 > 20, d'ou *le levier principal d'un arbre est presque absent de sa propre fourche*). Plus la **regle de frequence etendue au capstone** (§7, decision 23) et la **palette effective** (§5.0, decision 24). Sept invariants de plus (3 bis, 3 ter, 21 bis a 21 quater). - [docs/GAME_TRADES.md](docs/GAME_TRADES.md) — **Les metiers : recolte, artisanat, et ce qu'un arbre de metier decide** (proposition instruite, 2026-08-01) : second volet du chantier des arbres, annonce par GAME_ARCHETYPES §14. **Le constat mesure : 175 nœuds sur 190 sont des portes** — un arbre de metier ne dit pas *comment on travaille*, il dit *a quoi on a droit*. Un seul levier existe (`gather_percent`, +100 %), present sur 10 nœuds, **tous en recolte** (un forgeron qui a fini son arbre fabrique exactement comme un debutant, seulement **plus de choses**), et **ce levier fait deux choses a la fois** : `PurityDrawer` lit le bonus de **rendement** pour decaler la bande de purete, donc quantite et qualite sont **le meme curseur** et il n'y a rien a arbitrer. Ce qui change tout par rapport au combat : **le borneur n'est pas le combat, c'est le marche** — *un arbre de combat trop fort desequilibre un joueur, un arbre de metier trop fort desequilibre le serveur* —, d'ou la regle : **la progression d'un metier ne doit pas augmenter la quantite produite, elle doit deplacer la composition de ce qu'on produit et l'information qu'on possede** (trois familles d'effets classees par risque : la quantite gonfle le stock mondial, la composition le deplace, l'information ne cree rien). **Neuf leviers** (recolte : `yield`, `purity`, `stride`, `sight`, `care` ; artisanat : `finesse`, `tempo`, `thrift`, `batch`) avec taux de change, plafonds cales sur le risque economique, et budget de **50 pb** reutilisant la grille 3/6/9/14 du combat. **La fourche de recolte : Extraire / Preserver** — l'axe politique du jeu (GAME_WORLD §6) ramene a l'echelle d'une personne et d'une journee : *Extraire gagne la journee, Preserver gagne la saison, et ce que l'extracteur gagne aujourd'hui quelqu'un le repaiera au tresor demain*. **Les dents existent deja dans le code** (`vitality_ceilings` : sous 0,66 de vitalite plus aucun parfait ; `paleness.rise_per_pressure` 0,08 contre `daily_recovery` 0,04 — abimer va deux fois plus vite que reparer ; `VeinRestoration` qui donne un prix a la trace). **Un blocage racine mesure** : **la bande de purete n'a aucune valeur marchande** — aucun multiplicateur de prix nulle part ; `PurityChain` la propage et `CraftOrderManager` l'exige, elle a donc une valeur d'**usage** et jamais d'**echange**, ce qui rend toute branche « qualite » **strictement dominee**. D'ou le multiplicateur acte : trouble x1, clair x1,8, pur x3,5, **parfait x9**. Cote artisanat, les 7 metiers x 2 branches sont ecrits avec soin et **6 recettes sur 398** portent un `required_specialization` : la correction n'est **pas** d'en fermer davantage (*une recette fermee par branche disparait du serveur si personne ne prend la branche — en metier, un renoncement coute a tous les acheteurs*) mais de faire **deplacer la qualite** (`finesse` +8/−4, `tempo` −8 %/+4 %), les 6 pieces de signature restant fermees. Le **gabarit revu** ramene 175 portes a ~72 (*une porte ouvre un palier, jamais un objet*) et absorbe les 45 nœuds d'outil, qui sont des leviers deguises que personne n'arbitre. **Un exemple deroule** (§6, deux mineurs sur une journee) qui produit le meme constat que le combat sur un terrain sans tours : les deux branches font **2 740 contre 2 690 gils** (x1,02) en vendant **184 unites contre 140** dont **2x plus de bande haute** — et **sans son accord, l'extractrice perd 11 % de sa journee**, soit plus que ne lui rapportent ses 22 points de pourcentages. *Ce n'est pas le levier qui fait l'ecart, c'est l'accord.* Plus **10 invariants testables**, dont celui qui compte : **deux branches doivent gagner autant en vendant autre chose**. - [docs/GAME_TREE_ANATOMY.md](docs/GAME_TREE_ANATOMY.md) — **Anatomie d'un arbre de combat** (exercice instruit, 2026-08-01) : GAME_ARCHETYPES applique jusqu'au bout sur **cinq arbres — les trois registres et les quatre fonctions**. L'**Assassin** (tenebres x **melee** x assaut — le seul cas qui force a traiter la melee *en assaut*, la ou les quatre patrons ne la montrent qu'en encaisse) sert de methode. Le **Necromancien** (§12 — tenebres x **sorts** x controle) la met a l'epreuve : *meme element, meme marque, et rien en commun* — le test du voisin dans sa forme la plus dure. L'**Artificier** (§13 — feu x **distance** x controle) pose les dernieres mecaniques jamais ecrites dans un arbre (le carquois, `wind` converti en munition recuperee, la munition qui remplace l'element) et croise le test du voisin sur trois axes a la fois : element+marque avec le Pyromancien, fonction avec le Necromancien, registre avec l'Archer — *trois arbres, une seule marque, trois verbes : frapper dessus, la faire durer, la depenser*. Il porte aussi la seule tension d'archetype du jeu : **sa fonction allonge les combats et sa ressource se vide avec leur longueur**, ce qui fait de sa teinte (`wind`) une reparation plutot qu'un assaisonnement. Enfin le **Defenseur** et le **Gardien** (§14) sont ecrits en paire sur **la meme case** (terre x melee) : *seule leur fonction differe* — encaisse contre entretien —, ce qui demontre le troisieme axe sans qu'un seul chiffre ait a faire le travail, et pose deux mecaniques neuves (l'**aggro bornee** et le **depot de protection de groupe**). Ils ont trouve deux palettes amputees, **tranchees le 2026-08-01** : **`wind` n'avait aucune lecture en registre melee** (ecart 13 — un levier sur cinq inaccessible aux 8 arbres de melee ; il devient **la chance qu'une technique ne parte pas en reprise**, +1,0 pt/pb, forme imposee par le critere d'admission puisque `thrift` raccourcit deja la reprise : *le couple `guard`/`dodge` transpose sur la ressource*) et **la fonction encaisse ne peut pas acheter son levier principal** (ecart 14 → **decision 24, §5.0** : *la palette effective se calcule* — plafond du principal moins 14, soit 6 pb pour trois fonctions et **zero** pour l'encaisse, qui repartit donc 4 leviers et pose son sommet en `guard` ; ce qui **demontre** la these du canon — la mitigation d'un tank vient de son armure, pas de son arbre — et produit tout seul la meilleure fourche possible pour cette fonction : `dodge` contre `life`, eviter ou absorber). Il livre la fonction **controle** en entier, le **familier** (traite en depot offensif, ~1 tour d'attaque de valeur totale), une fourche qui oppose **le solo au donjon**, et la mesure qui les separe : l'Assassin **consomme** Aveugle (son capstone donne +28 % de degats contre une cible aveuglee), le Necromancien la **prolonge** (`grip`) — si bien qu'un assassin qui entre dans un combat deja tenu par un necromancien trouve son capstone allume des le premier tour, sans qu'aucune regle speciale ait ete ecrite. Il a aussi trouve **l'ecart n° 8**, porte au canon (§7.1 corollaire 2) : **le levier du capstone n'apparait jamais au palier 3** (14 + 9 > 20, le plafond le plus haut du jeu), d'ou une consequence contre-intuitive et vraie pour les 24 arbres — *le levier principal d'un arbre est presque absent de sa propre fourche*, qui est donc faite de ses leviers secondaires. Le document descend la ou la grammaire s'arrete : les **six natures de nœud** qu'un arbre peut contenir et **ce qu'un nœud ne peut jamais etre**, les 18 nœuds ecrits / 15 apprenables / 390 points / 50 pb par branche, chaque palier avec son calendrier et ses prerequis, la **variante pacte** entierement rechiffree, **ce que l'arbre ne contient pas et ou ca vit** (les gestes sont des materia, la mitigation est dans l'armure, la marque est un `StatusEffect` partage), les invariants passes un par un, le deroule du jour 1 au mois 3, et la forme du nœud en donnees (livre vs cible). Plus **les six materia de l'arbre** (§9 bis) : la derivation appliquee, la **grille de reprise** qui manquait a GAME_MATERIA (la melee paie le tour, pas les PM — 0/1/2/3/4 par palier, valeur qui tombe exactement sur le seul `cooldown` livre ; **portee au canon** avec la ligne munitions, ecart 7), et le constat qui vaut pour les 8 arbres de melee — **4 gestes sur 6 se reclassent, 2 sont a ecrire**. **Sept ecarts trouves ; les quatre premiers tranches le 2026-08-01 et portes dans GAME_ARCHETYPES** (§6.5 *ou se pose le pacte* — il **remplace** un passif de fourche, jamais un 19e nœud, et vit dans une seule branche, ce qui donne a la fourche son opposition la plus lisible : *la voie sure et la voie qui parie* ; §6.5 regle 7 + grille a deux crans — **19 pb ne tiennent que sous un plafond de 20**, donc un pacte majeur force le capstone a changer de levier : *un arbre a pacte est un autre arbre*, et le **pacte mineur a 5 pb** existe pour qui ne veut pas payer ce prix ; **§6.6 la loi des prerequis internes** — au plus un parent par nœud, **le capstone exige l'accord de branche jamais ses passifs**, aucun prerequis ne traverse la fourche, d'ou un chemin vers le sommet enfin lisible : *les cinq accords et rien d'autre*, 185 des 390 points ; **§7.1 le capstone ne vise qu'un levier de plafond ≥ 14 pb** — 7 leviers exclus d'office, et les 4 conditions canoniques cessent d'etre une coincidence). **Ecart 5 corrige** (2026-08-01) : les 12 echelons de port perdaient leur statistique dans une fuite mesurable — `assassin_weapon_t2/t3` donnait `critical +3` aux 4 domaines qui enseignent la dague, et les echelons du **baton** `heal +2` a **10** arbres dont 9 de sorts. La loi *un echelon est une porte, jamais une recompense* est desormais tenue par `rewireWeaponPortLadders()` et verifiee apres recablage. **Ecart 6 corrige** : les 24 accords dormants generes coutent 150 points et non 200 — la valeur heritee de l'echelle d'avant le gabarit ; sans effet (le nœud n'est pas apprenable), donc invisible jusqu'au jour ou la fusion l'aurait fait lire comme une decision. **Ecart 7 tranche** dans GAME_MATERIA (§2.3 bis) : **la ressource depend du registre** — une ligne par registre (PM 10/15/20/25/30, reprise **0/1/2/3/4**, munitions **1/2/3/4/5**), plus trois regles : *un geste ne facture que la ressource de son registre*, *aucune exception par intention* (une protection de melee part en reprise, une protection de distance consomme sa charge — le jeu s'auto-regule par le cout du tour), et un `cooldown` additionnel permis hors melee a partir du palier 3 comme garde-fou anti-spam. Restent : **l'arbalete qui n'existe ni en objet ni dans l'echelle de port** alors que le catalogue public la promet a l'Artificier (10) ; et **l'ecart 11, une contradiction du canon avec lui-meme** — le §7 accorde x2,0 au capstone « parce que sa condition peut manquer », quand le §4.3 impose x1,4 a une condition vraie plus des deux tiers du temps.
